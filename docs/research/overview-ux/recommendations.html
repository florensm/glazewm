Why it zooms out too much, and what to change

A full-screen window ends at 0.69× of its size today: four margins stack up, and the windows shrink inside a wallpaper slab that shrinks too. GNOME, KDE and macOS land near 0.8× with one margin. Eight changes, ranked, with the number to use and where it goes. Sources and the full comparison are in docs/research/overview-ux.md.

Click either desktop to try it yourself.

Where the size goes

A full-screen window on 1920×1080 at 100%, as each change lands. Computed with the same code as the playground.

Ranked changes

  1. Raise the cluster's cap

    0.85 → 0.94 of the room

    The room already has margins; the cap adds 7.5% more on every side. Alone, this takes a full-screen window from 0.69× to 0.77×.

    expose.rsLARGEST

  2. Thinner margins and wallpaper padding

    margins 48 → 32 px · padding 24 → 16 px

    With 1, windows end at 0.80× and fill 92% of the slab instead of 82%: the desktop and its windows shrink about alike, so the open reads as one depth, not two.

    layout.rs activities: marginparsed_config.rs OverviewWallpaperConfig::default: padding

  3. Open on a softer spring with a little give; close as today

    open spring(1, 800) → spring(0.85, 520) · close stays spring(1, 800)

    Same 90% at 140 ms, but within 1% by 196 ms and a 0.6% overshoot, so it lands instead of stopping. Closing stays fast, as exits should be. Needs the easing split into open and close.

    parsed_config.rs SpringParams::defaultOverviewAnimationConfig: open_easing, close_easing

  4. A small stagger by default

    stagger 0 → 10 ms, all within 60 ms

    Windows peeling off nearest-first read as windows moving apart, not a camera moving back. Too short to wait on. Open only.

    parsed_config.rs effects.stagger_msnative/scenes.rs ripple_delays

  5. A hover you can feel

    lift 0.025 → 0.04, title at once

    GNOME grows a hovered window 5 px each way, about 1.25%. At 0.8× scale, 4% is clearly felt without jumping.

    parsed_config.rs effects.window_lift

  6. Chrome arrives sooner

    from 80% → 60% open

    Names and highlights fade in while the windows still settle, so the overview feels ready sooner.

    layout.rs CHROME_FROM

  7. Dim the others slightly while pointing

    dim 0 → 0.12

    A lighter version of App Exposé's focus: the hovered window stands out without the rest going dark.

    parsed_config.rs effects.dim

  8. A slightly tighter gap

    gap 28 → 24 px

    With larger windows, 28 px looks wide. GNOME uses 6 px plus its preview chrome.

    parsed_config.rs expose.gap

Worth trying behind an option

A wallpaper that stays

wallpaper.style: "still": full screen, dimmed 25%, only the windows move, as on macOS. Removes the sense of depth entirely. Try it in the playground with "Stays, dimmed".

Rows for equal windows

Six equal tiles end at 0.81× in GNOME's rows and 0.65× in the cluster. With mixed sizes rows shrink the big window most, so only when windows are about the same size. See the layout comparison.

Search that dims in place

Switching studies favour layouts that keep windows where memory put them. Dim non-matches where they are instead of respreading the matches each keystroke. Try it in the feature lab.

Hint letters on Alt

Hold Alt and a letter shows on every window, as Hammerspoon's hints do; Alt+letter picks. Plain letters stay the search.

Peek

Hold a key to enlarge the selected window and check it, as Mission Control's spacebar does, without leaving the overview.

A readable floor

The top complaint everywhere is previews too small to recognise. Below about 0.45×, switch the crowded workspace to rows.

Hold to pick

Holding the binding's modifier makes the overview quasi-modal like Alt+Tab: arrows move, release picks. The quickest of the concepts.
